Chapter 1: Introduction

1.1 Project Overview

SecureBank is a full-stack digital banking web application built to demonstrate core Database Management System (DBMS) concepts in a real-world context. The application simulates a banking platform where users can authenticate, view their account dashboards, perform ACID-compliant fund transfers, and browse indexed transaction histories — all backed by a carefully designed PostgreSQL relational database.

The project integrates a Flask (Python) backend for server-side logic, a React.js frontend for a modern user interface, and a PostgreSQL database for persistent, reliable data management. The database schema implements key DBMS concepts including relational modeling with JOIN operations, stored functions with concurrency control, database triggers for automatic audit logging, B+ Tree indexing for fast retrieval, and BCNF-normalized table structures.

1.2 Purpose

The primary purpose of this project is to build a practical, working application that demonstrates the real-world usage of database management concepts covered in the BCSE302L course. Rather than demonstrating SQL queries in isolation, SecureBank embeds them into a functional banking workflow — making each concept tangible and observable during a live demonstration.

The project serves as an end-to-end showcase where:

  • The Login Page demonstrates SELECT queries and password-hashed authentication.
  • The Dashboard demonstrates INNER JOIN operations combining Customer and Accounts tables.
  • The Transfer Page demonstrates ACID transactions, stored functions, and row-level locking for concurrency control.
  • The Transaction History demonstrates B+ Tree indexed queries for fast retrieval by timestamp.
  • Triggers automatically maintain an audit log without any application-level code.

1.3 Scope

The scope of SecureBank covers the following functional areas:

  1. User Authentication: Secure login and session management using hashed passwords (scrypt algorithm via Werkzeug).
  2. Account Management: Display of savings/checking accounts with balances, account numbers, IFSC codes, and branch details.
  3. Fund Transfers: ACID-compliant fund transfers between accounts using a PostgreSQL stored function with SELECT ... FOR UPDATE row-level locking.
  4. Transaction History: Chronological display of past transactions, optimized with B+ Tree indexes on the timestamp column.
  5. Audit Logging: Automatic logging of every transfer and balance change via database triggers — fully transparent to the application layer.
  6. AI-Powered Fraud Detection: Basic statistical analysis flagging unusually large transfers based on historical transaction patterns.

1.4 Objectives

  1. Design a BCNF-normalized relational database schema with proper primary keys, foreign keys, and constraints.
  2. Implement INNER JOIN operations to combine related tables and display unified data.
  3. Demonstrate ACID transaction properties (Atomicity, Consistency, Isolation, Durability) through a stored function.
  4. Implement concurrency control using SELECT ... FOR UPDATE for row-level locking.
  5. Create database triggers that automatically log audit events without application-level code.
  6. Optimize query performance using B+ Tree indexes on frequently queried columns.
  7. Build a modern, responsive web interface with React.js to provide a realistic banking user experience.

Chapter 2: System Analysis

2.1 Limitations of Existing Systems

Traditional banking demonstration projects typically suffer from the following limitations:

# Limitation Impact
1 Console-based or static SQL-only demos Fail to demonstrate how databases integrate with real applications; hard to visualize during presentations.
2 No ACID transaction demonstration Fund transfers are implemented as raw SQL updates without transaction boundaries, rollback, or error handling.
3 No concurrency control Race conditions can cause lost updates when multiple transfers occur simultaneously on the same account.
4 Plain-text password storage Demo projects store passwords as plain text, demonstrating poor security practices.
5 No audit trail Changes to account balances are not logged automatically; manual logging is error-prone and unreliable.
6 Unindexed queries Transaction history retrieval performs full table scans, resulting in slow performance as data grows.

SecureBank addresses every limitation above with the following features:

3.3 Normalization

The SecureBank database schema has been designed to satisfy Boyce-Codd Normal Form (BCNF). Below is a step-by-step analysis of how each normal form is achieved.

1NF First Normal Form

Rule: Every column must contain only atomic (indivisible) values, and each row must be uniquely identifiable.

Analysis:
  • ✓ All columns store single, atomic values — no arrays, sets, or nested structures.
  • ✓ Every table has a SERIAL PRIMARY KEY ensuring unique row identification.
  • ✓ email and account_number are stored as single values with UNIQUE constraints.
  • ✓ Customer phone is stored as a single atomic value (not split into country code + number).

2NF Second Normal Form

Rule: Must satisfy 1NF, and every non-key attribute must depend on the entire primary key (no partial dependencies).

Analysis:
  • ✓ All tables use a single-column SERIAL primary key — partial dependencies are impossible with single-column keys.
  • ✓ In the Accounts table, account_type, balance, branch_name, etc. all depend entirely on account_id.
  • ✓ In TransactionHistory, amount, status, and transaction_type depend entirely on transaction_id.

3NF Third Normal Form

Rule: Must satisfy 2NF, and no non-key attribute can depend on another non-key attribute (no transitive dependencies).

Analysis:
  • ✓ In Customers: full_name, email, phone all depend only on customer_id, not on each other.
  • ✓ In Accounts: branch_name and ifsc_code are properties of the account, not derived from each other transitively. Each account independently stores its branch information.
  • ✓ Customer data (name, email) is stored only in the Customers table and referenced via FK — eliminating redundancy.
  • ✓ No table contains computed or derived data that could be obtained from other columns.

BCNF Boyce-Codd Normal Form

Rule: Must satisfy 3NF, and for every functional dependency X → Y, X must be a superkey.

Analysis:
  • ✓ Customers: Both customer_id (PK) and email (UNIQUE) are candidate keys. All FDs originate from superkeys.
  • ✓ Accounts: Both account_id (PK) and account_number (UNIQUE) are candidate keys. All non-key attributes depend on superkeys.
  • ✓ TransactionHistory: transaction_id is the only candidate key; all attributes depend solely on it.
  • ✓ AuditLog: log_id is the only candidate key; all attributes depend solely on it.
  • ✓ LoginActivity: activity_id is the only candidate key; all attributes depend solely on it.

Conclusion: All tables are in BCNF — every determinant is a superkey. No decomposition is required.

4.3 Stored Function — TransferFunds()

The TransferFunds() function is the heart of the ACID transaction implementation. It handles fund transfers between accounts with full atomicity, consistency, isolation, and durability guarantees.

ACID Properties Demonstrated

Property How It's Implemented
Atomicity Both the debit and credit operations exist inside a single function call. If any step fails, the EXCEPTION block catches the error and all changes are rolled back automatically.
Consistency Validation checks ensure: (1) both accounts exist, (2) the transfer amount is positive, and (3) sufficient balance exists before proceeding.
Isolation SELECT ... FOR UPDATE acquires row-level locks on both accounts, preventing other transactions from modifying them until the transfer completes.
Durability Once the application calls COMMIT, the changes are permanently stored in PostgreSQL's WAL (Write-Ahead Log).

Stored Function Code

CREATE OR REPLACE FUNCTION TransferFunds(
    p_from_account_id INTEGER,
    p_to_account_id INTEGER,
    p_amount DECIMAL(15, 2),
    OUT p_status VARCHAR(50),
    OUT p_message VARCHAR(255)
)
RETURNS RECORD
LANGUAGE plpgsql
AS $$
DECLARE
    v_from_balance DECIMAL(15, 2);
    v_to_balance DECIMAL(15, 2);
BEGIN
    -- Lock rows for update (Isolation - Concurrency Control)
    SELECT balance INTO v_from_balance
    FROM Accounts
    WHERE account_id = p_from_account_id
    FOR UPDATE;  -- Row-level lock

    SELECT balance INTO v_to_balance
    FROM Accounts
    WHERE account_id = p_to_account_id
    FOR UPDATE;  -- Row-level lock

    -- Validation Checks (Consistency)
    IF v_from_balance IS NULL THEN
        p_status := 'Failed';
        p_message := 'Source account not found.';
        RETURN;
    END IF;

    IF v_from_balance < p_amount THEN
        p_status := 'Failed';
        p_message := 'Insufficient balance. Transaction rolled back.';
        RETURN;
    END IF;

    -- Perform the transfer (Atomic operation)
    UPDATE Accounts SET balance = balance - p_amount
    WHERE account_id = p_from_account_id;

    UPDATE Accounts SET balance = balance + p_amount
    WHERE account_id = p_to_account_id;

    -- Record transaction in history
    INSERT INTO TransactionHistory
        (from_account_id, to_account_id, transaction_type, amount, status)
    VALUES
        (p_from_account_id, p_to_account_id, 'Transfer', p_amount, 'Success');

    p_status := 'Success';
    p_message := 'Transfer completed successfully.';

EXCEPTION
    WHEN OTHERS THEN
        p_status := 'Failed';
        p_message := 'Transaction failed. All changes rolled back.';
        RAISE;
END;
$$;

4.4 Database Triggers

SecureBank uses two database triggers for automatic audit logging. These triggers fire after relevant DML operations and insert records into the AuditLog table — without any application code needing to explicitly write audit entries.

Trigger 1: audit_transfer_access (AFTER INSERT on TransactionHistory)

CREATE OR REPLACE FUNCTION audit_transfer_access_func()
RETURNS TRIGGER LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO AuditLog (action_type, account_id, details, log_timestamp)
    VALUES (
        'Transfer Page Accessed',
        NEW.from_account_id,
        'Transfer initiated from Account #' || NEW.from_account_id 
            || ' to Account #' || NEW.to_account_id,
        CURRENT_TIMESTAMP
    );
    RETURN NEW;
END;
$$;

CREATE TRIGGER audit_transfer_access
AFTER INSERT ON TransactionHistory
FOR EACH ROW
EXECUTE FUNCTION audit_transfer_access_func();

Trigger 2: audit_balance_update (AFTER UPDATE on Accounts)

CREATE OR REPLACE FUNCTION audit_balance_update_func()
RETURNS TRIGGER LANGUAGE plpgsql
AS $$
BEGIN
    IF OLD.balance != NEW.balance THEN
        INSERT INTO AuditLog (action_type, account_id, details, log_timestamp)
        VALUES (
            'Balance Updated',
            NEW.account_id,
            'Balance changed from $' || OLD.balance || ' to $' || NEW.balance,
            CURRENT_TIMESTAMP
        );
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER audit_balance_update
AFTER UPDATE ON Accounts
FOR EACH ROW
EXECUTE FUNCTION audit_balance_update_func();

Note: With only 7 rows in the table, PostgreSQL's query optimizer chooses a sequential scan because it's more efficient for very small datasets. With larger datasets (thousands of rows), the optimizer would automatically use the idx_timestamp B+ Tree index for a much faster Index Scan. The index is created and ready — the optimizer is simply being smart about when to use it.

5.5 Trigger Verification — Audit Log

The audit log is populated entirely automatically by database triggers. No application code writes to this table — everything is handled at the database level.

log_id | action_type | account_id | details --------+------------------------+------------+-------------------------------------------------- 9 | Transfer Page Accessed | 1 | Transfer initiated from Account #1 to Account #4 8 | Balance Updated | 4 | Balance changed from $9210.00 to $10210.00 7 | Balance Updated | 1 | Balance changed from $3290.00 to $2290.00 6 | Transfer Page Accessed | 1 | Transfer initiated from Account #1 to Account #4 5 | Balance Updated | 4 | Balance changed from $7510.00 to $9210.00 4 | Balance Updated | 1 | Balance changed from $4990.00 to $3290.00 (showing 6 of 9 rows)
Key Observation: Each transfer operation generates exactly 3 audit log entries:
  1. "Balance Updated" for the sender account (triggered by audit_balance_update on Accounts UPDATE)
  2. "Balance Updated" for the receiver account (same trigger)
  3. "Transfer Page Accessed" for the transaction record (triggered by audit_transfer_access on TransactionHistory INSERT)
This demonstrates how triggers can automatically maintain a complete audit trail without any changes to the application code.

5.6 ROLLBACK Demonstration

This test demonstrates ACID Atomicity — when a transfer fails, all changes are rolled back to maintain consistency.

-- Start a transaction
START TRANSACTION;

-- Lock the row
SELECT balance FROM Accounts WHERE account_id = 1 FOR UPDATE;

-- Attempt an invalid transfer (more than balance)
UPDATE Accounts SET balance = balance - 999999 WHERE account_id = 1;

-- Check the balance (it would be negative — violation!)
SELECT balance FROM Accounts WHERE account_id = 1;

-- ROLLBACK to undo all changes
ROLLBACK;

-- Verify balance is unchanged
SELECT balance FROM Accounts WHERE account_id = 1;
-- Result: balance is still the original amount (unchanged)
